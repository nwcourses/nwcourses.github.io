Connecting to an API
--------------------

Last time you made a start on a HitTastic! React application, using a list of hard-coded songs. However a real application would need to work with a much bigger dataset, and would need to fetch the song data from a server, e.g. a JSON-based REST API. This is quite straightforward to implement when the app has been built for production: you can just add AJAX calls, using the `fetch` API, to the appropriate routes on the server which query the database and return JSON of all the matching songs.

However, what do you do when you are developing the app using the Vite dev server? Do you need to run two servers, the Vite server and your own API server?

You _could_ do this, as the Vite server is running on port 5173 by default whereas your own server is probably running on port 3000. So you could have the two servers running at once. However a little bit of work would be required:

*   You would need to explicitly state, in your AJAX calls from your React front-end, that you wish to connect to the server running on port 3000. This is because the front-end is being served from the Vite server on port 5173, so by default, AJAX calls will be to that same server running on port 5173. If you wish to connect via AJAX to another server, its port must be included.
*   Even if you did this, the AJAX calls would by default fail due to the Same-Origin Policy which states that the front end and back end of an AJAX application MUST come from the same domain name (`localhost` here) AND port. The ports are different so the AJAX calls will be blocked. We'd have to set up Cross-Origin Resource Sharing (CORS) on the server to enable it.

Luckily there is a better solution. The Vite server is designed to be run in _middleware mode_, in which it can be inserted into another server (such as an Express-based server) as middleware. Any routes which are not handled by your Express server (i.e. your front end) are then passed on to the Vite dev server running as middleware. So you can run your Express server, with Vite added as middleware, and continue to take advantage of Vite's Hot Module Reload facilities!

Vite provides a low-level API to do this. You can read about this [here](https://vitejs.dev/guide/ssr.html). This article is centred around the concept of server-side rendering, which we will meet later in the module, but also shows you how you can integrate Vite and Express. However the code is quite low-level and you have to manually handle the processing of `index.html`. In the words of that page:

> If your goal is to create an application, make sure to check out the higher-level SSR plugins and tools at [Awesome Vite](https://github.com/vitejs/awesome-vite#ssr) \[...\] instead.

Awesome Vite is a GitHub repo which contains a range of third-party tools for working with Vite. A particularly interesting tool is [vite-express](https://github.com/szymmis/vite-express) which integrates Vite with Express. Using `vite-express` you can create an Express server with the Vite dev server included as middleware with minimal code.

You need to install `vite-express` first, e.g:

npm install vite-express

You can then use it in a simple server:

import express from 'express';
import ViteExpress from 'vite-express';

const app = express();

ViteExpress.listen(app, 3000, () => "Express server with Vite integration now running...");

### What about production?

A particularly useful feature of `vite-express` is that the server you create is _also suitable for production_, in which case the Vite dev server will _not_ be used. In production mode, you bundle your app with `npx vite build` as before, and then start your server by passing in the environment variable `NODE_ENV` set to a value of `production`:

NODE\_ENV=production node server.mjs

`vite-express` tests the environment variable `NODE_ENV` and if it's set to `production`, it will run your server _without_ including the Vite dev server as middleware. Instead, it will serve the built bundle and static assets from the `dist` folder.

### Using Effects

The exercise asked you about where to place code to send an AJAX request to the server when the component first loads. Where could it go?

*   You could add it directly inside the component function. However this is incorrect. The component function is purely for _rendering_ and should not contain any slow operations, such as connecting to the network. Re-rendering can potentially be done at any time, whenever React sees fit to do so, and is certainly done whenever state changes. In our app, the user may want to change the mode (light or dark), updating the state, and in this case we certainly do not want to make another request to the server to retrieve all songs!
*   It could be placed in an ordinary function and called from the top of the component function. This would make the code cleaner but would have the same problem as above.
*   The correct place to add the code is in an _effect_, as we saw in the [further React notes](/COM518/topic7.html) last year. If you remember, an effect is a function used to perform a time-consuming external task which can be run either at _every render_, the _first render only_ or _when selected state variables or props change_. We run an effect by using `React.useEffect()` with a function as a parameter which performs the external task, such as an AJAX call.

Here is another exercise on the use of effects.

### Exercise 3 Discussion: Specifying when an effect will run

In this case, you want the effect to run _only when the component is first loaded_, because that is the only time we need to load all the songs. There is _no_ need to run the effect each time state updates, for example. There are three ways to call an effect:

*   Call it on _every_ render;
*   Call it on _first_ render only;
*   Call it _only when particular state variables or props change_.

As we saw in the [notes last year](https://nwcourses.github.io/COM518/topic7.html), you specify when the effect should be called via the second argument to the `useEffect()` function:

*   `useEffect( effectFunction )` alone will run the effect on every render. **This is not what we want.**
*   `useEffect( effectFunction, [ variable1, variable2, variable3 ... ] )` alone will run the effect _whenever any of the variables listed inside the array change. These variables can be either state variables or props._ Again this is **not what we want as we only want to load the effect when the component first loads**.
*   `useEffect( effectFunction, [] )`, i.e. with an empty array as the second argument, runs the effect on _first render only_. **This is what we want here.**

Designing Reusable React Components
-----------------------------------

A key concept in React component design is to ensure the components are _reusable_. Whenever we create a React component, we should be thinking: _might we want to use this component again, in a completely different application?_

We are now going to do a small analysis and design exercise. Take a look at this problem statement for an extended version of HitTastic!:

*   HitTastic! is a website to allow users to search for, and buy, music. A user should be able to search for songs by artist. If they are logged in, they should be able to buy music by clicking on a "Buy" button on the user interface. An administrator should be able to add new songs to the database.

### Possible Components for HitTastic!

From the in-class discussion we worked out that these components might be useful to have in the HitTastic! app to implement the search facility:

*   A _search_ component, allowing the user to enter a search term.
*   A _results_ component, allowing the results to be displayed.
*   A _login_ component, displaying a login form if the user is not logged in, or a "Logged in as..." message if they are logged in.
*   An _add new song_ component, containing a form allowing the user to add a song to the database.
*   An app component, containing all these components.

We want each of these components to be reusable. So the search component, for example, can work in isolation, without needing the `App` component. How can this be done? Read the notes from [last year](https://nwcourses.github.io/COM518/topic7.html), in particular the notes on Lifting Up State and answer these questions:

### Passing data between components and lifting up state

As we saw last year, we can adopt a _callback-based approach_ by which we pass a _function_ (a callback) into the search component as a prop. Whenever the user performs a search, this function is called. Because the function is defined by the developer, passed in as a prop, it means that each app can implement its _own way_ of handling the search. The callback would probably be a function in the parent component (e.g. the `App`).

We introduced the topic of _lifting up state_ [last year](https://nwcourses.github.io/COM518/topic7.html). The technique of _lifting up state_ is useful if we need to share state (such as an array of songs) between several components. We store the state in the parent component and then pass it to child components as _props_.
