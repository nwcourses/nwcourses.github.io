Server-side Rendering
---------------------

Traditionally, React has rendered on the client-side, in the browser. JavaScript code running in the browser receives React components from the server, parses them and renders them. Communication with the server takes place via AJAX requests, as we have seen, with the server typically sending back JSON which is then transformed into JSX on the client side. Such applications are generally known as _Single-Page Applications (SPAs)_, because all the functionality is contained within a single HTML page, even if the content changes when the user interacts with the applicatiom. This is the same approach that non-React AJAX applications take.

Even though SPAs have been perhaps the leading type of web application recently, there are some advantages to rendering the page _on the server_ instead. For example, if all rendering is done on the server, the client need not download the React JavaScript library and browser loading times are faster because the browser is just loading HTML rather than having to parse JSX. It can also be better for Search Engine Optimisation (SEO) because HTML is easier to handle for search engines than JavaScript. (see [the Digital Ocean article](https://www.digitalocean.com/community/tutorials/react-server-side-rendering) which discusses these advantages).

There are of course disadvantages of server-side rendering: for example many clients will potentially connect to a server, meaning that the server might have to render pages in response to many requests coming in from different clients. Thus, the server could potentially become overloaded to a greater extent than if it simply sends back JSON to clients for the server to deal with. However this can be mitigated by the server caching the HTML pages generated by parsing the JSX server side.

Nonetheless despite these disadvantages there has been a lot of interest in React server-side rendering in the last two years or so due to the advantages discussed above, and thus it is an important topic to cover.

Server-side Rendering and React Server Components
-------------------------------------------------

In React server-side terminology, there are two slightly different concepts: _server-side rendering_ (SSR) and _React Server Components_ (RSC).We will discuss each.

### Server-side rendering

SSR is the simplest of the two concepts. It simply involves using the `react-dom/server` module (as opposed to the usual `react-dom/client` module) to render strings of JSX as HTML server-side. Here is a basic example of an Express server to do this.

import express from 'express';
import path from 'path';
import fs from 'fs/promises';

import React from 'react';
import ReactDOMServer from 'react-dom/server';
import App from '../src/components/app.mjs';

const PORT = 3000;

const app = express();

app.use(express.static('public'));

app.get('/', async(req, res) => {
    const app = ReactDOMServer.renderToString(<App />);
    const indexFile = path.resolve('./html/index.html');
    try {
        const data = await fs.readFile(indexFile, 'utf8');
        res.send(
            data.replace("<div id='root'></div>", \`<div id="root">${app}</div>\`)
        );
    }catch(err) {
        res.status(500).send(err);
    }
});

app.listen(PORT, () => {
    console.log(\`Server running on port ${PORT}.\`);
});

Much of this is just standard Express but note the detail of the `/` route. Note how we use `ReactDOMServer.renderToString()` to render our `App` JSX component to pure HTML. We then load our `index.html` and read it into memory as a string with `fs.readFile()` from the `fs` (filesystem) package. We then replace the `root` div inside the HTML with a `root` div containing the HTML parsed from the JSX and send it back to the client.

#### How do we run this server? It contains JSX!

You might be wondering though: **this server contains JSX (`<App />`), so how will Node.js handle the JSX when it encounters it? Is it not a syntax error?**

The answer is: it is a syntax error, so we do not run this server directly with `node`. Instead we have to _transpile_ it, for example with Babel. We could use Webpack to do this, here is an example of a Webpack config which will do it (`webpack.server.config.js`):

const path = require('path');
const nodeExternals = require('webpack-node-externals');

module.exports = {
    mode: 'development',
    target: 'node',
    entry: './server/index.mjs',
    externals: \[nodeExternals()\],
    output: {
        path: path.resolve('server-build'),
        filename: 'index.js'
    },
    optimization: {
        minimize: false
    },
    module: {
        rules: \[
            {
                test: /.(js|jsx|mjs)$/,
                use: {
                    loader: "babel-loader"
                }
            }
        \]
    }
}

Note how we specify our server (with JSX, as above) using the `entry` property and then define an output server in standard JavaScript (no JSX) in the `output` property. So the output server will be placed in the `server-build` folder. It's _this_ server we run.

### The client

The server will send back the output HTML but what if we want event handling, e.g. we want to handle events such as button clicks? How can we do this if it was rendered on the server, given that events are client side?

The answer is that we have to _hydrate_ the HTML returned from the server. Here is an example of a client-side `index.jsx` which will do this:

import React from 'react';
import ReactDOM from 'react-dom/client';
import App from './components/app.mjs';

ReactDOM.hydrateRoot(document.getElementById('root'), <App />);

Rather than _rendering_ `App`, which we have already done server-side, we _hydrate_ our React root instead. This means to convert it from static HTML (sent back from the server) to a "living" web page with event handling added. The `App` specified here is the _same_ `App` that was rendered server-side (see above).

### Building the app

We must use a bundler, such as Vite or Webpack, to both _transform the server from JSX to plain JavaScript_ and _produce a client-side bundle to perform the hydration_. For example a `package.json` for an SSR project might include a `scripts` section like this:

{
  "name": "react-ssr",
  "version": "0.0.1",
  "scripts": {
    "build": "npx webpack; npx webpack --config webpack.server.config.js",
    "build-client": "npx webpack",
    "build-server": "npx webpack --config webpack.server.config.js",
    "start": "node server-build/index.js"
  },
  ...
}

Note the different build scripts:

*   _build_ (`npm run build`) will build both the client side and server side;
*   _build-client_ (`npm run build-client`) will build the client side;
*   _build-server_ (`npm run build-server`) will build the server side;
*   _start_ (`npm start`) will start the server.

Note that we will need _two_ `webpack.config.js` files, one for the client and one for the server.

A full example is available [on GitHub.](https://github.com/nwcourses/react-ssr)

React Server Components
-----------------------

React Server Components (RSC) are components which "render ahead of time, before bundling, in an environment separate from your client app or SSR Server" (see [React documentation](https://react.dev/reference/rsc/server-components)). The idea is that code in Server Components are rendered _before_ any bundling takes place, at build time. This allows them, for example, to read files or query a database on the machine where the bundling takes place. They can be used **without a server running**: in this case the build tool will download any dependencies before executing the code. As RSC code is run as part of the build process, its dependencies will not need to be included in the bundle sent to the client, minimising bundle size.

### Using RSC without a server, e.g. as a preprocessor

Here is an example **taken directly from the React documentation** (it can be found [here](https://react.dev/reference/rsc/server-components)). Apologies for re-using the official React example rather than coming up with my own, but I think it perfectly illustrates React Server Components and why you might want to use them even if you are not running a server.

import marked from 'marked';
import sanitizeHtml from 'sanitize-html';
import fs from 'fs/promises';

async function Page({page}) {
    const content = await fs.readFile(\`${page}.md\`);
    return <div>{sanitizeHtml(marked(content))}</div>;
}

`marked` and `sanitizeHtml` are third-party libraries which would be installed by `npm` or another package manager. `marked` is used to convert Markdown to HTML, and `sanitizeHtml` processes the HTML to help prevent any cross-site scripting (XSS) attempts.

If we run this as an RSC, it will be run on the server (or more generally, the machine which does the bundling) meaning that only this machine need have `marked` and `sanitizeHtml` installed. We need not include these libraries in the bundle sent to the client.

.

As the React documentation notes, this code need not be part of a web server. You can run it as a preprocessor on a machine to convert all your Markdown files to HTML and then upload the generated static HTML files to a server ready for users to view.

### Using RSC with a server

We can, as the name might suggest, also run RSC as part of a _web server_. As discussed on the React documentation referenced above, server components can be rendered in response to the first request from the client, with the rendered components (i.e. the HTML output from the JSX rendered server-side) included in the bundle in addition to client-side components (which will contain JSX and be rendered on the client). An example might be a server component to render all pizzas available on a pizza-ordering website. The server component would query the database to find all the available pizzas, and then render that list of pizzas. The server component would output HTML and this HTML would then be sent to the client within the bundle, in addition to any client-side components needed.

It should be noted that RSC are distinct from SSR (Server Side Rendering). SSR simply involves using the `react-dom/server` package to render strings of JSX on the server-side to produce HTML. RSC on the other hand are entire components that are designed to be processed at the bundler stage when being built. Optionally, RSC can use SSR to render JSX strings as HTML while this bundling stage is taking place.

### Mixing server- and client-side components

We might want to mix server-side and client-side components in the same application. Why might we want to do this? RSC cannot include any _interactivity_, such as allowing the user to fill in a form and click a button. In our pizza-ordering application, the user might wish to add a pizza to their basket by interacting with the application. This might involve the user entering a quantity and clicking a button.

What we'd do here is _mark client side components as client-side using the directive:_

"use client"

If you are developing a system with a mix of both, the default is to assume server components. So anything without `use client` will be an RSC.

Here would be an RSC to render all pizzas. Note how each pizza is repesented by a <PizzaOrder> sub-component.

export default async function AllPizzas() {
    
    // Code to setup database not shown. This is just generic example code.
    const pizzas = await db.query("SELECT \* FROM pizzas");

    const output = pizzas.map (pizza => 
        <PizzaOrder pizza={pizza} />
    );
    return <div>{output}</div>
}

Here is the `PizzaOrder` subcomponent:

"use client"

export default function PizzaOrder({pizza}) {


    return <div>
        Pizza flavour: {pizza.flavour} <br />
        Pizza price: {pizza.price} <br />
        <button onClick={order(pizza.id)}>Order!</button>
        </div>

    function order(pizzaId) {
        // functionality to order the pizza (not shown)
        // This might involve sending an AJAX request to a server or even
        // using a Server Action (see later)
    } 
}

Note how it uses interactivity. Thus we cannot make this a server component. However we can mark it with `use client` and _include it within a server component as a child_.

You should also note that you _cannot use effects or state in server components_, so if you want to use either, you must include them in a client component and then make the client component a child of your server component.

Note that client-side components within an RSC app can be processed in two different ways:

*   The JSX can be sent back to the client to be rendered;
*   The JSX can be processed server-side using SSR, and then sent back to the client to be _hydrated_ (see SSR discussion, above).

Implementation of React Server Components
-----------------------------------------

React does not provide an "official" implementation of a server to process RSC but leaves it up to third-party providers to implement. In this session, we will use one of the simplest and most accessible third-party providers, `@lazarv/react-server`, referred to from now on as `_react-server_`, created by Viktor Lázár. `react-server` includes an inbuilt, Node-based server which will process RSC; you do not have to create your own server. In the next topic we will then move on to the _Next.js_ framework.

When using `react-server`, it is recommended to use the package manager `pnpm`: using `npm` has some difficulties. You can install pnpm using npm:

npm install -g @pnpm/exe

Note how this is _just a component_. However, you can run it directly using `react-server`: `react-server` will process it server side and output the HTML to the client.

### Server Actions

Server-based React applications typically take a different approach to server-side functionality such as interacting with a database. Rather than APIs, RSCs query the database directly and generate JSX based on the contents of the database (as seen in the pizza example above). However what about _updates_ on the server, i.e. updating the database in some way in response to a POST request? These are typically implemented using _server actions_.

Server actions are functions executed on the server typically in response to the user entering data in a form and then sending it to the server as a POST request. Rather than writing, for example, an Express POST route, we write our server functionality as a simple _function_ and set our form's _action_ to this function. An RSC environment then performs some behind-the-scenes magic on this code: under the hood it's still a standard HTTP POST request being processed by a server.

Server actions must be called by a _client component_. They must also be marked by the directive:

"use server"

to indicate that they run on the server.

#### Client component communicating with a server action

Here is an example client component which calls a server action:

"use client";

import { addSong } from './actions/addsong.js';
import { useActionState } from 'react';

export default function AddSong() {

    const \[ state, addSongWithState \]  = useActionState(addSong, { });
    return <div>
        <form action={addSongWithState}>
        <h1>Add Song</h1>
        Title:<br />
        <input name='song' id='song' /><br />
        Artist:
        <input name='artist' id='artist' /><br />
        Year:
        <input name='year' id='year' type='number' /><br />
        <button type='submit'>Go!</button>
        </form>
        State: { JSON.stringify(state) }
        </div>;
}

What's going on here?

*   You'll notice that the component renders an HTML form to allow the user to add a song. Note how the form's _action_ is `addSongWithState`, a _function_.
*   Where does this function come from? Note how we _import_ `addSong` from `actions/addsong.js`. This is our server action, and we will look at it in detail later. However what we are also using here is using _action state_. Action state allows us to share state between client side components and server actions. However, to do this we need to convert our original server action `addSong` to a version which can use action state: `addSongWithState` here. To do this we use the React `useActionState()` hook:
    
    const \[ state, addSongWithState \]  = useActionState(addSong, { });
    
    `useActionState()` takes two arguments: the original server action fuunction, and an object to represent the state (originally empty). It returns an array containing two members: a state variable (which will contain state returned from the server action), and a modified server action which will work with action state.
*   For the moment we display the state after the form using `JSON.stringify()` to convert it to JSON.

#### The server action

Meanwhile, here is the actual server action:

"use server";

import Database from 'better-sqlite3';

export async function addSong(prevState, formData) {

    const title = formData.get("song"),
          artist = formData.get("artist"),
          year = formData.get("year");

    const db = new Database("wadsongs.db");

    const stmt = db.prepare("INSERT INTO wadsongs(title,artist,year) values(?,?,?)");
    const info = stmt.run(title, artist, year);
    return { info };
}

*   Note how the server action is a function, as we've discussed above. It takes two parameters, `prevState` (the previous value of the action state), and `formData` (a FormData object, representing the form data: we looked at these last week with React Router actions).
*   Note how we read the form data and then perform an INSERT query on our SQLite database.
*   Note also how we _return_ the information object returned from the server when we do the INSERT (this will contain the number of rows inserted (`changes`) and the ID of the row inserted (`lastInsertRowid`)). Critically, **the return value of the server action becomes the action state**. So, whatever is returned by the server action will become the `state` in the client component. As we display the `state` in our client, it follows that we will see the information returned from the database on the client as soon as the server action has completed.

Using react-server and Express
------------------------------

We can combine `react-server` with an existing Express server, allowing you to make use of existing API routes on your server. This is achieved by running react-server in _middleware_ mode, i.e. it acts as a middleware for your Express server. This means that Express will handle all routes matching a certain pattern by forwarding them on to react-server, while all others will be handled directly by Express. By doing this you can easily write an app which features both RSCs and JSON APIs.

Here is an example, note how any route beginning with `react-server` will be handled by react-server:

import express from 'express';

// This assumes development mode.
// You need a different import for production mode.
// See the Express example at https://github.com/lazarv/react-server/tree/main/examples/express for more detail.

import { reactServer } from '@lazarv/react-server/dev';

const app = express();

// Assumes App.jsx contains the app component
// If we pass no arguments to reactServer(), filesystem routing will be used.
const server = await reactServer('./App.jsx');

const PORT = 3000;

app.get('/', (req, res) => {
    res.send("Hello World from Express!");
});

app.use('/react-server', async(req, res, next) => {
    const { middlewares } = await server;
    middlewares(req, res, next);
});

// Add other routes and middleware, e.g. API routes, here...

app.listen(PORT, () => {
  console.log(\`Server started on port ${PORT}.\`);
});

For this to work you must configure a `base` URL in the configuration file `react-server.config.json` (in the top level folder of your project):

{
  "base": "/react-server/"
}
